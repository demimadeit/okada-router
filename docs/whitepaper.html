The Okada Protocol

How an AI gateway keeps answering when the network, the provider, or the power fails — and what that is worth to a company that runs on unreliable infrastructure.

okada-router · August 2026 · github.com/demimadeit/okada-router

Every AI product ever shipped assumes the same four words: the network is up. Okada removes that assumption. It sits between an application and the model providers, measures the connection continuously, and picks where each individual request should be answered — full cloud model, cheaper cloud model, another provider, cache, a model on the device itself, or a queue that delivers later.

01The assumption that fails

The standard architecture is a single unbroken line: app → internet → cloud API → answer. Every hop must succeed. There is no second path, so when any hop fails the user gets a spinner and then an error.

In markets where that line is unreliable, the failure is not an edge case, it is the daily condition:

27,000+fibre cuts in Nigeria, Jan–Nov 2025 (NCC)
~190days/yr of firm-level power downtime — Nigeria topped the World Bank Enterprise Survey 2024, as reported by Guardian NG
~104msbest-case Lagos→London RTT floor; frontier models are served from the US/EU
2×rise in the price of 1GB of mobile data, 2023→2025

Three distinct things break, and they break independently: the user's link (radio congestion, fibre cut, dead tower), the provider (outage, rate limit, a model quietly retired), and the budget (data costs money per megabyte). A retry loop addresses none of them. It just fails more expensively.

02The mechanism

Okada is an OpenAI-compatible HTTP endpoint. An application adopts it by changing one line — the base URL — so no application code, SDK, or prompt has to change. What happens behind that endpoint is the product.

Network sensing

A background loop probes on a three-second rotation and keeps a ten-sample window per target. Two classes of target are measured separately, because they answer different questions: generic anycast endpoints establish whether the last mile is alive at all, and each configured provider's own endpoint establishes whether the path to that specific inference provider is healthy. A healthy route to Google implies nothing about the route to a model provider — different transit, different submarine path, different POP. Measured on one laptop at one moment: generic internet 97ms, path to the model provider 249ms. Physically switching off WiFi was detected in about six seconds, with no human input.

This is still coarse. Production-grade sensing would ingest carrier, ASN, cell site, route, RTT per provider, DNS and TLS setup time, and historical performance by time of day — which is also precisely what turns the telemetry into a moat rather than a log file.

The decision

Routing is a deterministic policy — first match wins. Rules are used rather than a learned model on purpose: a rule can be explained to a customer, debugged at 2am, and it produces the labelled decision log that a learned policy would later need as training data.

# first match wins, evaluated per request
if cache_hit                      → cache        # ~0ms, 0 bytes
if offline                        → device model # else queue
if primary provider unhealthy     → alternate provider
if latency > 2500ms or loss > 25% → device model # beats a retry storm
if latency > 600ms  or loss > 5%  → small cloud model + response cap
else                              → full cloud model

The chosen rung is the start of a chain, not a final answer. If it fails mid-request, execution walks downward — full model to small model to alternate provider to device to queue — so a failure degrades the answer instead of destroying it.

What actually reduces bytes

A claim worth stating carefully, because the intuitive version is false: switching to a smaller model does not by itself send fewer bytes. The prompt is unchanged, the API envelope is unchanged, and a smaller model can emit just as many output tokens. The model swap buys cost per token, not transfer.

So the degraded rungs carry an explicit response cap — that is the mechanism that actually shrinks the payload, and it is what the router applies today. Genuine bandwidth engineering — prompt and context compression, request deduplication, protocol-level compression, and a binary transport on the leg where Okada controls both ends — is roadmap, not shipped. Streamed responses carry roughly five to twenty-five times the bytes of the text they deliver, so that leg is where the remaining savings live.

Why the bottom rung matters

The queue is the last rung because writing a request to disk requires no network and no model. It is replayed when connectivity returns and the result is retrievable by id.

State this precisely, because the loose version is wrong: a queued request is not an answered request. The correct claim is that requests are answered, degraded, or durably accepted for later execution — never silently dropped and never returned as a bare failure. Today the queue survives a network outage but not a process restart, so even "durable" carries an asterisk until that is fixed.

03What was measured

Two experiments, both reproducible from the public repository. Read them as engineering evidence that the routing works, not as market statistics: 56 requests against a simulated network is a demo benchmark. It shows the mechanism behaves as designed under controlled degradation. It does not establish production reliability, and the numbers below should not be quoted as what Okada delivers on a real carrier.

Honest reading: Okada is slower under heavy packet loss (p95 8.4s vs 1.9s). The direct call only appears faster there because a quarter of its requests failed outright, and failed requests are not timed. The trade is seconds in exchange for answers that arrive at all.

The real-work test

A benchmark measures reliability; it does not prove usefulness. So a genuine commercial task was run with the laptop's WiFi physically switched off: research a fragrance brand's identity and produce a seven-section launch report for its first collection.

6sto self-detect the dead link
82sto write the report, offline
623tokens generated on-device
0bytes of network used

The offline report was complete and usable — and measurably worse than the cloud version produced minutes later. It invented price points, and it proposed relaunching a product line the brief stated was sold out. The cloud version respected that constraint and made a reasoned recommendation instead of listing options.

That gap is not a defect to hide. It is the product's actual promise, stated precisely: a degraded answer you can work from, instead of no answer at all.

04A company using it

Illustrative scenario

Sabi Pay is a payments company with 40,000 agents running kiosks across Nigeria — a market kiosk in Aba, a shopfront in Kano, a table under an umbrella in Surulere. Each agent has a phone app with an AI assistant that answers the questions that actually cost the business money: why did this transfer fail, what is the fee on this amount, what does this error code mean, how do I reverse a payment.

Before Okada, that assistant used a single cloud API. It worked beautifully in the Lagos office and unpredictably everywhere the agents actually are. Every failed answer became a call to the support centre, or a customer walking away.

One agent, one afternoon. Nothing here is configured by hand; every line is a decision Okada made from its own reading of the network.

The agent noticed none of this. From their side the assistant simply answered every time — sometimes brilliantly, sometimes briefly, once with a short delay. The support centre received zero calls that afternoon that started with "the app is not working."

Where the value is concentrated

Note which failures Okada actually converts. A dead radio mast is beyond any software's reach — Okada cannot fix it, and claiming otherwise would be dishonest. What it does is ensure that a dead mast produces a shorter answer rather than a broken product. For a business with tens of thousands of field staff, that distinction is the difference between a feature people trust and a feature they stop opening.

The distinction matters and is easy to get wrong: a gateway on a remote server cannot answer a phone that has no signal, because that phone cannot reach the gateway either. Offline capability lives wherever the model lives.

06What is not yet true

The cache is exact-match and single-tenant. No semantic matching, no PII handling. Not safe for multi-tenant use.

Streaming is not incremental. Responses are delivered complete rather than token by token, which costs perceived speed on slow links.

The queue is journaled but not replayed after a restart. Durable across a network outage, not yet across a power cut.

No encryption at rest, no tenant isolation. Both are prerequisites before any customer's data touches a shared deployment.

No mobile SDK. Today only machines running Okada themselves get the offline path.

A gateway cannot fix a dead radio link or an unpowered tower. It can only survive them. That is the honest boundary of what is being claimed.

07Why this becomes defensible

Every individual component here exists as open source. The gateway pattern is commoditised, and both mobile platform owners are moving toward device-and-cloud APIs. So the moat is not the code.

It is the record. Every request writes one line: the network state observed, the decision made, the reason, each attempt and its outcome. Multiplied across carriers, cities and hours, that becomes something no competitor can copy without occupying the same position — knowledge of which route will succeed before the request is sent. A router that knows a given network degrades every evening at seven can move traffic before the failure rather than after it.

The second asset is the transport layer. Streamed AI responses carry five to twenty-five times more bytes than the text they deliver, because of protocol framing. A gateway that controls both ends of the connection can re-encode that traffic. In a market where the price of data doubled in two years, saving most of it is not an optimisation — it is the reason a company adopts you.

08Corrections in this revision

This version was revised after external technical review. The changes are listed because a whitepaper that quietly edits its own claims is worth less than one that shows them:

Sourcing tightened. The ~190-day power downtime figure is Nigeria's, and Nigeria did top the World Bank Enterprise Survey on this measure — but it was cited here as if taken from a primary World Bank document when the accessible source is secondary reporting. Now attributed precisely.

Claim removed. "No AI inference on the continent" was too broad and is withdrawn: Bedrock exposes a Cape Town endpoint and Cloudflare has deployed Workers AI GPUs in Lagos. The defensible statement is narrower — frontier models are served from the US and EU, so a Lagos request still crosses a submarine cable.

Reliability language corrected. "No path ends in try again" overstated it. A queued request is not an answered request, and the queue does not yet survive a restart.

Benchmark reframed. 56 simulated requests is engineering evidence, not a market statistic, and is now labelled as such.

Bandwidth mechanism fixed in code. The routing reason previously claimed a smaller model "cuts transfer". It now applies an explicit response cap, which is the thing that actually does.

Sensing deepened in code. Probing generic endpoints was insufficient; each provider's own path is now measured separately. First measurement on one machine: 97ms to a generic endpoint, 249ms to the model provider.
